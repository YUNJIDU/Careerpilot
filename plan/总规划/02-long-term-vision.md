# AI Job Application Copilot 长期项目规划

更新时间：2026-07-20

## 1. 产品愿景

构建一个以求职者为中心的辅助求职 Agent：

- 从用户已经查看和理解的邮件中同步、提取并汇总申请记录。
- 根据当前阶段提供恰当的信息，而不是一次性堆砌所有内容。
- 保存每个岗位使用的简历、JD、邮件证据、准备材料和结果。
- 在用户主动触发后辅助研究和资料整理；填报、训练和复盘作为后续扩展。
- 最终可从本地单用户工具演进为安全的多租户 Web 产品。

系统不是“无监督海投机器人”，也不替用户盯邮箱、理解事件或做求职决策。默认用户了解自己的全部求职情况，系统作为第三方记录与辅助工具工作。

## 2. 核心原则

1. 数据库是唯一事实源，Excel 是用户友好的同步/导出视图。
2. 确定性流程优先，Agent 后置。
3. 事实、推断和建议分开保存。
4. 所有外部信息必须保留来源和抓取时间。
5. 邮件、网页、附件均为不可信输入。
6. 自动化必须可暂停、可审计、可重试。
7. 先支持单用户本地运行，再考虑多租户和商业化。
8. 核心业务逻辑优先 Python；前端和数据库通过清晰边界替换。
9. 首发产品以本地 Web 为主要入口，Excel 为双向统计视图，Markdown 为岗位详情和 Summary。
10. 邮件同步只提取和保存客观信息，不引入额外确认队列或替用户作决定。
11. 采用 Open Core：本地核心框架开源，SaaS 商业能力通过稳定接口与核心隔离。

## 3. 用户主流程

### 3.1 发现与投递

1. 用户手工创建岗位，或由邮件/浏览器流程创建。
2. 保存公司、岗位、JD 链接、JD 快照、渠道、申请时间和简历版本。
3. 根据 JD 生成申请前检查项。
4. 后期可生成定制简历、求职信和表单答案。
5. 自动填报默认停在提交前，用户确认后才提交。

### 3.2 邮件驱动的状态更新

1. 用户手动触发邮件同步；可选本地定时同步默认关闭。
2. 规则做初筛，排除明显无关邮件。
3. 解析器提取公司、岗位、事件、日期、阶段和置信度。
4. 将邮件信息关联到 Application，并保留来源和证据。
5. 写入不可变邮件事件和当前统计快照。
6. 双向同步 Excel；不自动触发联网研究或模型任务。

### 3.3 阶段化准备

- 已投递：岗位摘要、公司摘要、技能差距、下一步。
- 笔试/OA：形式、考点、题型、练习计划、限时模拟。
- 面试：轮次、可能问题、岗位知识、STAR 故事、反问问题。
- Offer：条款、截止日期、对比、谈薪准备。
- 拒绝：可证实原因、过程数据和改进实验；不把猜测写成事实。

### 3.4 个性化训练

1. 上传一份或多份简历。
2. 解析技能、项目和经历，并允许用户修正。
3. 将 JD 要求映射到简历证据。
4. 生成针对岗位和阶段的题目。
5. 记录答案、评分依据、薄弱点和复习计划。
6. 用后续表现更新掌握度，而不是简单累计聊天记录。

## 4. 领域模型

### 4.1 核心实体

#### Application

- `id`
- `user_id`
- `company_id`
- `job_title`
- `status`
- `applied_at`
- `source`
- `job_url`
- `jd_snapshot_id`
- `resume_version_id`
- `location`
- `employment_type`
- `salary_text`
- `notes`
- `created_at`
- `updated_at`

#### ApplicationEvent

- `id`
- `application_id`
- `event_type`
- `event_at`
- `source_type`
- `source_id`
- `confidence`
- `is_user_confirmed`
- `payload`
- `created_at`

当前状态应由已确认事件和状态规则计算。事件不应因状态变化而被覆盖。

#### EmailRecord

- 标准化邮件元数据
- 邮件正文摘要
- 原始哈希
- 分类结果
- 解析版本
- 处理状态
- 关联 Application

#### Company / JobDescription

- 公司规范名称与别名
- 官方域名
- JD 原文/快照/哈希
- 来源 URL
- 抓取时间
- 结构化职责、要求、技能和关键词

#### Artifact

统一表示：

- 简历版本
- 求职信
- 表单答案
- 笔试报告
- 面试报告
- 模拟练习
- 复盘报告

#### ResearchSource / ResearchClaim

每个结论保留来源、时间、可信度和证据片段。报告中的事实应能回溯到来源。

### 4.2 状态机

建议初始状态：

`DRAFT → APPLIED → OA → INTERVIEW → OFFER → ACCEPTED`

终止或旁路状态：

- `REJECTED`
- `WITHDRAWN`
- `GHOSTED`
- `ARCHIVED`

要求：

- 同一 Application 可有多轮 OA/Interview 事件。
- 邮件提取不得把不确定推断写成事实；不明确字段留空，并始终保存来源和证据。
- 状态回退必须有原因和审计记录。
- 同一公司不同岗位必须是不同 Application。

## 5. 逻辑架构

### 5.1 第一形态：模块化单体

一个 Python 服务内分成清晰模块：

- `mail_ingestion`
- `application_tracking`
- `document_processing`
- `research`
- `preparation`
- `export`
- `model_gateway`
- `audit`

这些模块共享数据库，但只能通过服务接口修改领域数据。

### 5.2 外部边界

- 邮件适配器：163/IMAP、未来 Gmail/Outlook。
- 模型适配器：云模型或本地模型。
- 抓取适配器：普通 HTTP、Crawl4AI、浏览器自动化。
- 文件存储：本地目录，未来对象存储。
- 前端：本地 Web，具体框架在 Stage 4 详细设计时确定。
- 导出：Excel，未来 CSV/API/Webhook。

### 5.3 数据流

`用户了解邮件 → 本地同步 → 客观信息提取 → 来源化事件 → 数据库/Excel → 用户手动触发资料整理 → Markdown/Web`

每一步记录：

- 输入版本
- 处理器版本
- 模型/提示词版本
- 输出
- 错误
- 人工修正

## 6. 分期路线

### Phase 0：需求与样本

- 收集脱敏邮件样本。
- 定义状态和字段。
- 建立 10–30 条人工标注样本。
- 固定 Excel 初始模板和状态映射。

### Phase 1：本地信息底座

- 本地 Web。
- Excel 与数据库双向同步。
- 统一邮箱接口、本地邮件样本与 163 只读同步。
- 客观信息提取、证据和必要附件。
- Application CRUD 和事件时间线。
- 每个岗位一份 Markdown 详情文档。

验收：邮件信息可可靠地形成或更新申请记录，用户修改不被静默覆盖，所有信息可回溯来源。

### Phase 2：手动触发的岗位情报

- JD 链接与快照。
- 公司/岗位公开信息检索。
- 来源管理。
- 按 OA/Interview 阶段生成不同报告。

验收：用户主动触发后生成公司、JD、笔试或面试 Summary；事实可追溯，阶段不串线，重复内容可缓存。

### Phase 3：个性化准备扩展

- 简历上传和版本管理。
- JD-简历证据映射。
- 笔试题目、模拟面试、语音训练和基于明确量表的反馈。
- 错题与掌握度。

验收：每条建议能指向 JD 要求和简历证据。

### Phase 4：申请辅助

- 可复用个人资料。
- 表单答案库。
- 浏览器 dry-run。
- 人工审批后填报/提交。

验收：任何写操作有预览、审批和审计；失败不会重复提交。

### Phase 5：Orchestrator Multi-Agent

首发使用单一主辅助 Agent 调用稳定工具。只有当确定性流程和单 Agent 出现明显编排瓶颈时，才采用 Orchestrator 协作模式并引入：

- Orchestrator
- Mail Triage Agent
- Job Research Agent
- Resume Agent
- OA Coach
- Interview Coach
- Review Agent

Agent 之间传递结构化任务和结果，不共享无限聊天上下文。

### Phase 6：持久任务与记忆

- 路由：按任务类型、风险、成本和阶段选择流程。
- 检查点：长任务可暂停和恢复。
- 短期记忆：单次任务上下文。
- 长期记忆：用户偏好、答案库、技能掌握度。
- 跨 Agent 共享：通过受控数据服务，不直接互读私有 Prompt。

### Phase 7：多租户 Web 产品

- 用户、组织、角色和权限。
- 密钥托管和租户隔离。
- 异步任务、队列、限流和配额。
- 对象存储、PostgreSQL、备份和灾难恢复。
- API、Web 前端、支付和订单。

面向普通用户时演进为云端 Web/SaaS。当前不决定本地版届时继续维护、作为社区版保留，还是被 SaaS 替代；核心业务模块必须保持可移植，避免本地版和 SaaS 形成两套业务实现。

### Open Core 边界

计划开源的核心框架：

- Application Core 与数据契约。
- Excel 双向同步。
- MailAdapter 与基础邮箱适配器。
- ModelGateway。
- Summary、Agent 和工具接口。
- 本地 Web。
- 插件/扩展接口、安全测试和迁移机制。

当前只保留接口、不编写实现：

- 支付。
- 配额。
- 运营系统。
- 托管凭证服务。
- 商业专属集成。

这些商业能力的开源与实现策略留到 SaaS Stage 再决定。

### Phase 8：商业化

可能形式：

- 本地个人版。
- 单次交付/授权版。
- Web 订阅。
- 小红书等渠道的模板、部署或咨询服务。

商业化前必须处理隐私政策、用户授权、数据删除、模型供应商条款、招聘网站条款、支付与售后。

## 7. Agent 与 Function Calling 的长期设计

### 7.1 不让 Agent 直接拥有数据库写权限

Agent 输出结构化建议或命令候选，由应用服务验证后执行。

### 7.2 工具分级

- 只读：查 Application、读 JD、搜索公开信息。
- 低风险写入：保存草稿、生成报告。
- 高风险写入：发送邮件、提交申请、删除数据、覆盖状态。

高风险工具必须人工批准。

### 7.3 MCP 的位置

先将内部能力实现为普通 Python 函数/API，接口稳定后再包装为 MCP：

- `mail.search`
- `applications.get/update`
- `research.fetch`
- `documents.parse`
- `practice.generate/grade`

MCP 是工具协议，不承担业务事务、权限或跨 Agent 记忆。

### 7.4 Orchestrator

Orchestrator 负责：

- 判断任务类型。
- 分配 Agent/确定性工作流。
- 限制预算、时间和工具范围。
- 汇总结果。
- 触发人工审批。

它不负责保存所有业务事实；事实仍在数据库。

## 8. 记忆策略

### 短期

- 当前 Application
- 当前阶段
- 当前任务输入
- 本次工具结果

任务结束后只保留需要审计的摘要。

### 长期

- 用户确认过的个人资料。
- 可复用表单答案。
- 简历项目证据。
- 技能掌握度和错题。
- 用户偏好和人工修正。

### 禁止记忆

- 邮箱密码或授权码。
- 不必要的完整邮件正文。
- 模型臆测的个人事实。
- 未经确认的拒绝原因。

## 9. 安全与隐私

### 本地阶段

- 邮箱只读。
- 凭证使用环境变量或系统密钥库。
- 日志脱敏。
- 附件类型、大小和解析超时限制。
- Excel 公式注入防护。
- 抓取域名白名单和请求限速。
- 所有外部内容与系统指令隔离。

### 多租户阶段

- 租户级行权限或独立 schema。
- RBAC/ABAC。
- 短期凭证和密钥轮换。
- CSRF、SSRF、XSS、SQL 注入、文件上传和 Prompt Injection 防护。
- API 限流、配额和审计日志。
- 后台任务幂等和重放保护。
- 加密备份、恢复演练、数据导出和彻底删除。

## 10. 可观测性与评测

至少监控：

- 邮件读取/解析成功率。
- 分类准确率和人工修改率。
- Application 匹配准确率。
- 状态误更新率。
- 抓取成功率、来源覆盖率和缓存命中率。
- 报告事实引用率。
- LLM 成本、时延和失败率。
- 自动填报 dry-run/真实提交成功率。

建立固定评测集：

- 邮件分类。
- 公司/岗位实体抽取。
- Application 匹配。
- 阶段路由。
- JD 结构化。
- 笔试/面试报告质量。
- Prompt Injection 和敏感信息泄露。

## 11. 服务拆分触发条件

默认不拆微服务。只有满足以下条件才拆：

- 邮件同步与 Web 请求资源冲突。
- 抓取任务需要独立扩缩容。
- 浏览器自动化需要隔离运行。
- 模型任务需要独立限流/队列。
- 多租户安全边界要求独立部署。

可能的最终服务：

- API/Auth
- Mail Ingestion
- Application Core
- Research Worker
- Browser Worker
- AI Gateway
- Artifact Storage
- Notification

## 12. 长期完成标准

- 用户能从投递到 Offer/拒绝完整追踪。
- 所有关键状态有证据和历史。
- 阶段化材料与真实岗位相关且可追溯。
- 自动化失败后能安全恢复，不重复提交。
- 用户能查看、更正、导出和删除自己的全部数据。
- 多用户之间数据、凭证和任务严格隔离。
- 商业化版本有明确的安全、隐私、合规和运维责任。
