# CareerPilot 首发版本计划

更新时间：2026-07-26

## 1. 产品定位

CareerPilot 是辅助求职 Agent，不是替用户完成求职的全权 Agent。

优先级：

1. 先满足项目作者本人的实际求职记录和资料整理需求。
2. 首批提供给同专业、懂 AI、能够本地部署的技术用户。
3. 开发过程同时形成可展示的 AI/Agent 项目和研究案例。
4. 核心闭环稳定后，再考虑面向普通用户的产品化。

默认用户会自行查看、理解全部求职邮件，并负责所有判断和决策。系统作为第三方记录与辅助工具，只提取客观信息、保存证据、维护 Tracker，并在用户主动触发时整理公开资料。

## 2. 首发目标

跑通以下闭环：

```text
本地 Web 配置邮箱
  → 用户手动同步新增邮件
  → 提取客观求职信息
  → 保存数据库、证据片段和必要附件
  → 双向同步 Excel Tracker
  → 查看每个岗位的详情和时间线
  → 用户手动生成公司/JD/笔试/面试 Summary
  → 在本地 Web 或 Markdown 中查看
```

首发成功的标准是：信息能够可靠收集、保存、更新、回溯和整理，而不是 Agent 替用户做决定。

## 3. 首发范围

### 必须包含

1. 本地 Web 页面作为主要操作入口。
2. 统一 `MailAdapter`，首个真实适配器支持 163 IMAP。
3. 本地 `.eml`/JSON 样本导入，用于测试和故障回退。
4. 手动邮箱同步；可选本地定时同步，默认关闭。
5. 从收件箱指定时间范围读取邮件，不要求用户整理邮箱文件夹。
6. 提取公司、岗位、投递与阶段信息、日期、截止时间、链接及必要说明。
7. Application、邮件时间线、来源和证据片段。
8. 本地数据库与 Excel Tracker 双向同步。
9. 每个 Application 一份独立 Markdown 详情文档。
10. 用户手动触发公司、JD、公开笔试和面试资料 Summary。
11. 本地数据优先；模型支持本地与云端切换。
12. 基础日志、错误恢复、幂等和端到端测试。
13. 核心框架采用 Open Core 边界，为后续扩展保留稳定接口。
14. 邮箱、Excel、附件、Summary 和迁移任务具备用户可见的任务状态与断点恢复。

### 后续扩展

- 模拟题、模拟面试、自动评分和训练计划。
- 未读邮件监控、主动提醒、截止时间紧急通知和多渠道推送。
- Gmail、Outlook 等更多邮箱适配器。
- 验证码处理模块。
- 成熟自动填表项目的模块化接入。
- Multi-Agent Orchestrator。
- 普通用户产品化、多租户和商业化。

### 明确不做

- 岗位发现、职位推荐和招聘网站聚合。
- 替用户决定是否投递、是否参加、是否接受或拒绝。
- 将推断写成用户事实。
- 登录第三方内容账号。
- 绕过反爬、验证码或付费墙。
- 自动投递或自动提交。
- 首发版本中的复杂训练系统。

## 4. 产品形态

### 本地 Web

主要操作入口，至少包括：

- 邮箱和模型配置。
- 手动同步。
- Tracker 查看。
- Application 详情与时间线。
- 附件与证据查看。
- Excel 导入、同步与导出。
- 手动生成或更新 Summary。
- Markdown 查看。

具体 UI 布局在 Stage 4 开始前单独设计。

### 首发技术栈

- Python 负责核心业务。
- FastAPI 提供 `/api/v1` 后端接口。
- React + TypeScript + Vite 构建本地 Web。
- Pydantic 定义数据契约。
- SQLAlchemy + SQLite 提供本地持久化。
- Alembic 从首版管理数据库迁移。
- openpyxl 负责 Excel 双向同步。

Windows 是首要开发和验收环境；核心闭环跑通后提供 Docker。Windows 原生版与 Docker 版复用同一业务逻辑和数据 Schema。

### Excel Tracker

Excel 只承担信息统计、状态更新、快速参考和双向编辑，不保存长篇 Summary。

主表列：

| 投递时间 | 公司名称 | 岗位 | 简历通过 | 测评 | 笔试 | 一面 | 二面 | 三面 | HR 面 | 终面 | 当前阶段 | 截止时间 | JD 链接 | 最近更新时间 | 备注 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|

阶段单元格采用简短的“日期 + 结果/安排”，例如：

- `7.17 笔试安排`
- `7.17 笔试挂`
- `7.22 一面通过`
- `7.25 二面待结果`

超过固定列能够表达的特殊轮次，记录到备注和岗位详情文档。

### Markdown

每个 Application 一份独立 Markdown，例如：

```text
贵州金控-投资业务.md
```

包含：

- 公司与岗位基本信息。
- JD 原文引用与摘要。
- 申请时间线。
- 邮件证据引用。
- 必要附件链接。
- 笔试公开资料及来源。
- 各轮面试公开资料及来源。
- Summary 生成时间和版本。

同一公司的通用资料可以缓存复用，但不同岗位不得混成同一份文档。

## 5. 邮箱同步边界

### 统一接口

业务层只依赖统一邮箱接口，不绑定具体供应商。首发真实适配器为 163 IMAP，后续通过新增适配器支持 Gmail/Outlook。

### 运行方式

- 默认由用户手动点击同步。
- 可选本地定时同步，默认关闭。
- 定时同步只更新记录，不承担提醒或决策职责。
- 首发不要求实时推送或云端常驻服务。

### 读取范围

- 默认读取收件箱指定时间范围。
- 先用邮件头和规则进行低成本筛选，再读取候选邮件正文。
- 不要求用户建立专用文件夹。

### 保存范围

默认长期保存：

- 标准化邮件元数据。
- 结构化提取结果。
- 必要摘要和证据片段。
- 原始邮件哈希。
- 与 Application 的关联。

默认不长期保存完整原始 MIME 和完整正文。需要重新解析时，从邮箱只读获取原邮件；若原邮件已删除，应明确标记原文不可回看。

### 附件

- 默认只检测并提示疑似承载笔试、面试、JD 等必要信息的附件。
- 用户确认后下载并关联 Application。
- 高级用户后续可以开启白名单附件自动下载，默认关闭。
- 只允许安全白名单格式并限制大小。
- 禁止执行宏、脚本和压缩包内容。
- 保存来源邮件、哈希、下载时间和本地路径。

## 6. 数据与同步原则

### 数据职责

- 本地数据库保存完整结构化数据、证据、历史、附件关系和 Artifact。
- Excel 是用户可直接编辑的主要统计视图。
- Markdown 是岗位详情和 Summary 载体。

### 双向同步

- 数据库的新提取信息更新到 Excel。
- 用户在 Excel 中的修改同步回数据库。
- 用户手工修改始终优先。
- 邮件新信息作为新事件或历史追加，不得静默覆盖用户值。
- 同时保留邮件提取值、用户修改值、来源和时间。
- 清空字段必须区分用户明确删除与未知/未提取。

具体冲突检测、隐藏 ID 和版本字段在 Stage 1 设计时确定。

## 7. 信息提取边界

系统提取邮件中明确表达的客观信息：

- 公司和岗位。
- 投递、简历筛选、测评、笔试和面试安排。
- 一面、二面、三面、HR 面和终面。
- 日期、时间、截止时间和链接。
- 邮件中明确给出的结果或要求。

系统不得：

- 推断用户应该采取什么行动。
- 判断岗位是否值得申请。
- 替用户接受、拒绝或撤回。
- 将不确定推断写成确定事实。

不明确的信息可以留空。证据片段和来源始终随记录保存。

## 8. Summary 边界

Summary 由用户在具体 Application 上手动触发，不随邮件同步自动联网或调用模型。

输入：

- 公司和岗位。
- JD 文本或链接。
- 当前已记录阶段。
- 用户已经保存的邮件信息。

输出：

- 公司公开信息。
- 岗位和 JD 摘要。
- 与当前阶段有关的公开笔试信息。
- 与当前轮次有关的公开面试信息。
- 来源、抓取时间和不确定性。

首发不生成模拟题、模拟面试、评分或训练计划。

公开资料边界：

- 允许访问无需登录的公开信息。
- 禁止登录第三方内容账号。
- 禁止绕过反爬和付费墙。
- 验证码处理留作后续模块。
- 具体来源和抓取策略在 Summary Stage 开始前细化。

## 9. 模型与数据边界

- 邮件、Excel、数据库、附件和 Markdown 默认全部保存在本机。
- 外部搜索和云模型仅在用户主动触发对应功能时调用。
- 对外发送前裁剪姓名、邮箱、电话、完整邮件正文等非必要个人信息。
- 模型层支持本地模型和云模型切换。
- 技术用户可选择完全本地运行。
- Web 页面明确显示当前操作是否会让数据离开本机。
- 外部内容和模型输出均视为不可信数据，经过 Schema 和业务规则校验。

## 10. Agent 演进

### 首发

采用一个主辅助 Agent，调用普通 Python 工具：

- 邮箱同步与解析工具。
- Application 与 Excel 工具。
- 公开资料检索工具。
- Summary 生成工具。

核心模块不依赖 Agent，也可以单独测试和调用。

### 后续 Multi-Agent

采用 Orchestrator 协作模式。Orchestrator 负责任务分配、工具权限、预算、超时和结果汇总；专用 Agent 只处理各自领域，不直接任意修改业务数据库。

Multi-Agent 不作为首发完成条件。

### Open Core 原则

首发本地核心框架计划开源，包括数据契约、Application Core、Excel 同步、MailAdapter、ModelGateway、Summary/Agent 工具接口、本地 Web 和安全测试。

支付、配额、运营系统、托管凭证和商业专属集成只保留外部接口或扩展点，首发不编写实现，也不提前锁定其内部设计。

开源核心采用 Apache License 2.0。未来商业模块放在独立包或仓库中，许可证另行决定。

### 扩展接口

- 从首版定义可版本化的 MailAdapter、ModelGateway、Summary Provider、Attachment Parser 和后续表单适配器接口。
- 首发只加载项目内置、明确启用的适配器。
- 首发不允许任意安装和执行第三方插件。
- 开放插件生态前必须具备权限声明、最小授权、签名、来源、沙箱、兼容和撤销机制。
- 插件不得直接读取全部数据库、邮箱凭证或任意本地文件。

## 11. 首发阶段

### Stage 0：契约与安全

固定数据模型、Excel Schema、邮箱接口、模型接口、文件边界和安全原则。

### Stage 1：本地数据底座

实现数据库、Excel 双向同步、用户修改优先和导入/导出。

### Stage 2：Application Core

实现 Application、邮件时间线、来源证据、附件关系和 Markdown 路径。

### Stage 3：邮箱与提取

实现本地样本、163 只读同步、客观信息提取和 Tracker 更新。

### Stage 4：本地 Web 与 Summary

实现主要 Web 操作入口、岗位详情、手动 Summary 和完整端到端链路。

Stage 0–4 完成即为可交付给首批技术用户的版本。

## 11.1 本地用户与数据目录

- 首发严格单用户，不实现本地注册、登录、角色和权限系统。
- 单用户可管理多份简历和多个邮箱账户。
- 数据统一放在 `data/` 目录体系中。
- 只定义 BackupService、RestoreService 和数据删除接口；完整备份、恢复、迁移和彻底删除功能后置。

## 12. 首发完成门槛

1. 用户能在本地 Web 配置并手动同步 163 邮箱。
2. 同一邮件重复同步不会重复写记录。
3. 客观求职信息能保存到数据库并更新 Excel。
4. 用户编辑 Excel 后能安全同步回数据库。
5. 用户值不会被后续邮件同步静默覆盖。
6. 每条记录能够回溯到邮件来源和证据片段。
7. 必要附件可以安全下载并关联岗位。
8. 每个岗位都有独立 Markdown 详情文档。
9. 用户能手动生成公司/JD/笔试/面试 Summary。
10. Summary 中的公开事实带来源和抓取时间。
11. 邮箱、网络、模型或 Excel 失败不会破坏已有数据。
12. 本地模型与云模型边界对用户可见。
13. 一条端到端测试覆盖：

```text
163/样本邮件
  → 提取
  → 数据库
  → Excel
  → Excel 用户修改
  → 数据库
  → 手动 Summary
  → Markdown/Web
```

### 框架最低质量门槛

- 数据模型、字段来源、同步冲突和安全规则单元测试。
- SQLite、Excel、MailAdapter 和 ModelGateway 桩集成测试。
- FastAPI、React、样本邮件和 Excel 端到端冒烟测试。
- Excel 公式注入、路径穿越、恶意附件名、邮件 Prompt Injection 和敏感日志泄漏测试。
- 测试使用固定脱敏样本和模型桩，不连接真实邮箱或付费模型。
- Python/TypeScript 静态检查、格式检查、依赖漏洞扫描和 secret scanning。
- Windows 是首要 CI/验收环境，Docker 构建是第二验证链。

### 可恢复任务

- 长流程统一生成 `job_id`。
- 保存任务类型、状态、当前步骤、检查点、错误码、脱敏说明、重试建议和处理器版本。
- 只有成功提交的事务才能推进检查点。
- 从断点继续必须复用幂等键，不产生重复事件、附件或 Summary。
- 技术日志与用户可见任务记录分离。

## 13. 后续再决策

- 未读监控、提醒和通知渠道。
- 模拟题、模拟面试和训练系统。
- Gmail/Outlook 适配器。
- 验证码处理。
- 自动填表项目的选择与接入方式。
- Orchestrator 下的具体 Agent 划分。
- 面向普通用户的部署和商业模式。
- 多租户、支付、高并发和云端托管。
- 本地版在 SaaS 阶段继续维护、转为社区版或停止独立演进。

这些内容保留在后续 Stage 中；进入对应 Stage 时再单独访谈和细化。
