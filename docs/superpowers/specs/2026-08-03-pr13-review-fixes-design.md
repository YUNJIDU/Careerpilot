# PR #13 审查问题修复设计

## 目标

在不改变现有公开 API、用户数据和 PR #13 功能范围的前提下，修复审查发现的四项问题：Docker 暴露范围、OAuth 断开后的内存令牌、不可复现的初始迁移，以及 OAuth 邮箱身份未核对。

## 修复设计

### Docker 本机边界

所有用户可复制的 `docker run` 命令必须将 `9998` 和 `9999` 显式发布到 `127.0.0.1`。容器内 Uvicorn 继续监听 `0.0.0.0`，因为容器网络需要该监听方式；安全边界由宿主机端口发布地址实现。CI smoke test 同样使用 loopback 发布，防止示例和验收行为分叉。

### OAuth 断开

`OAuthCoordinator.disconnect()` 必须同时删除 Secret Store 中的令牌和 `runtime_tokens` 中的缓存。删除持久化令牌失败时保持当前错误语义，不把连接误报为已断开。回归测试覆盖“过期令牌刷新到内存、随后断开、再次取令牌失败”。

### OAuth 邮箱身份核对

授权码交换成功后，后端使用新访问令牌读取服务商账户信息：Gmail 调用 Gmail Profile，Outlook 调用 Microsoft Graph `/me`。服务商返回的邮箱经 `strip().casefold()` 规范化后必须与启动授权时登记的邮箱一致；缺失或不一致时不保存令牌，并返回安全的授权失败信息。测试不访问真实服务，继续通过注入的 HTTP 函数提供确定性响应。

### 可复现迁移

`0001_initial.py` 改为显式创建当时的初始表，不能导入当前 ORM `Base`。从空库升级时，`0001` 到 `0009` 的每个迁移只负责自己的结构。

对于有表但没有 `alembic_version` 的 legacy 数据库，stamp `0002` 前验证 `0002` 所需核心表；结构不足时明确失败，避免把未知 SQLite 文件伪装成 `0002`。现有已标记为 `0002` 的用户数据库升级路径不变。

## 错误处理与兼容性

- 不修改已有数据库表、API 路径或请求结构。
- OAuth 邮箱不匹配不会写入令牌，也不会覆盖已有账户身份。
- migration 校验失败时不执行 stamp 或后续升级；升级前备份机制继续保留。
- 已有 `0002` 数据库可继续逐版本升级到 `0009` 并降回 `0002`。

## 验收

1. Docker 文档与 CI 中的宿主机端口均绑定 `127.0.0.1`。
2. OAuth 刷新后断开，再次读取访问令牌必须失败。
3. Gmail 和 Outlook 邮箱匹配时连接成功，不匹配或缺失时不保存令牌。
4. 空数据库完整升级到 `0009`，且各阶段表在对应迁移后才出现。
5. 合法 legacy `0002` 数据库可以迁移；不完整 legacy 数据库拒绝 stamp。
6. 现有数据库副本升级、完整性检查、外键检查和回滚数据守恒均通过。
7. GitHub Actions 五项检查全部通过。

## 非目标

- 不增加登录、远程部署或多租户能力。
- 不重建现有用户数据库。
- 不调整 Stage 5–7 的业务功能和页面布局。
- 不引入新的运行时依赖或抽象层。
